# Оцінювання за критеріями: дизайн

Дата: 2026-10-09. Статус: затверджено в обговоренні, чекає на план реалізації.

## 1. Мета

Замінити зашиту в код рубрику (результат 70, порядок 15, конструкції 15, частковий бал
за збіг рядків, 0.5 за прихований набір, стеля 85) на набір бінарних критеріїв,
які викладач вмикає для кожної вправи, і поріг «достатньо N з M».

Що лишається без змін: порівняння результатів як мультимножин, EXCEPT ALL,
нормалізація значень, приховані набори, перевірка наборів мутантами, ізоляція виконання,
таймер уроку, спроби, сума балів за урок, відсоток за курс.

## 2. Модель оцінки

- Для вправи визначено список критеріїв. Кожен критерій після перевірки має рівно один
  стан: пройдено або не пройдено. Стану «пропущено» немає.
- `passed_count` = кількість пройдених, `total` = кількість критеріїв у перевірці,
  `threshold` = поріг.
- Вправа зарахована, якщо `passed_count >= threshold`.
- Бал = `max_score`, якщо зарахована, інакше 0. `is_correct` збігається з «зарахована».
- Бал за урок = сума найкращих балів за вправи. Відсоток за курс не змінюється.

## 3. Каталог критеріїв

### 3.1. Загальні (вмикає викладач)

| id | Назва | Застосовність |
|---|---|---|
| `execution` | Запит виконується | завжди; вимкнути не можна |
| `columns` | Кількість стовпців як в еталоні | SELECT на SQL, MongoDB, Redis |
| `column_names` | Назви стовпців як в еталоні | SELECT на SQL |
| `complete` | Усі потрібні рядки є | SELECT на SQL, MongoDB, Redis |
| `precise` | Немає зайвих рядків | SELECT на SQL, MongoDB, Redis |
| `order` | Порядок рядків як в еталоні | SELECT, тільки якщо еталон містить ORDER BY; MongoDB, Redis: завжди доступний |
| `reads_data` | Відповідь отримана запитом до таблиць | SELECT на SQL, якщо еталон сам не константний |
| `state` | Стан таблиць після запиту збігається з еталонним | еталон INSERT, UPDATE, DELETE, CREATE TABLE |

Тип вправи визначає еталонний запит, як і зараз (`classify_statement`):
SELECT-подібний еталон дає набір для вибірки, інший еталон дає набір для зміни даних.
Для MongoDB і Redis набір для вибірки без `column_names` і `reads_data`.

`complete` і `precise` разом еквівалентні збігу мультимножин. Окремого критерію
«значення збігаються» немає, щоб один факт не рахувався двічі.

### 3.2. Похідні (з'являються з полів вправи, вимкнути можна лише прибравши поле)

| id | Назва для студента | Джерело |
|---|---|---|
| `dataset:<k>` | Контрольний набір №k | k-й елемент `check_datasets`, нумерація з 1 |
| `require:<KW>` | Використано KW | елемент `required_keywords` |
| `forbid:<KW>` | Не використано KW | елемент `forbidden_keywords` |

Назва прихованого набору і його опис (`targets`) студенту не показуються в списку критеріїв.
Після провалу в поясненні критерію показується `targets`, як зараз у підказках.

### 3.3. Для вправ без еталона

Якщо еталонного запиту немає і немає збереженого результату (`expected_result`),
застосовні лише `execution`, `reads_data` і похідні за ключовими словами.
Збережений результат (`expected_result`, застарілий режим) далі працює як еталон
для `columns`, `complete`, `precise`, `order`, `column_names`.

## 4. Налаштування вправи

Поле `criteria` (JSON) на `LessonExercise` і `Assignment`:

```json
{"enabled": ["execution", "columns", "complete", "precise", "order"], "threshold": 4}
```

- `enabled`: список id загальних критеріїв. Похідні в список не входять, вони завжди активні.
- `threshold`: ціле число. Якщо відсутнє, 0 або більше за `total`, під час перевірки
  береться `total` (усі критерії).
- Порожній об'єкт або `null` означає налаштування за замовчуванням.

За замовчуванням увімкнено всі застосовні загальні критерії, крім `column_names`,
поріг = усі. Для старих вправ це зберігає поточне значення «правильно»:
`order` входить у замовчування лише якщо еталон містить ORDER BY або увімкнено
застаріле поле `order_matters`.

Поле `order_matters` лишається в моделі лише для побудови замовчування; форма його
більше не показує і не змінює. Поле `partial_match` у завданнях не використовується.

### 4.1. Валідація при збереженні

- `enabled` містить лише відомі id загальних критеріїв.
- Кожен id застосовний до вправи: `order` вимагає ORDER BY в еталоні (перевірка через sqlglot),
  `reads_data` і `column_names` лише для SQL-баз і SELECT-еталона, `state` лише для еталона
  на зміну даних, `columns`/`complete`/`precise` лише для SELECT-еталона.
- `execution` завжди додається, навіть якщо його немає в списку.
- `threshold` ціле від 0. Більше за кількість критеріїв не є помилкою, під час перевірки
  підрізається до «усі» (кількість похідних може змінитися після збереження).
- Повідомлення про помилки українською, як і решта текстів оцінювання.

## 5. Перевірка (`backend/grading/criteria.py`)

### 5.1. Реєстр

```python
@dataclass
class Criterion:
    id: str
    name: str
    evaluate: Callable[[Context], Verdict]   # Verdict(passed: bool, detail: str)

def catalog(task) -> list[Criterion]           # загальні, застосовні до задачі
def derived(task) -> list[Criterion]           # dataset:k, require:KW, forbid:KW
def resolve(task, config) -> list[Criterion]   # увімкнені загальні + похідні, execution першим
def describe(task, config) -> dict             # {"criteria": [{"id","name"}], "threshold": N}
```

### 5.2. Контекст

Будується один раз на перевірку і обчислює дорогі речі ліниво, з кешем:

- виконання запиту студента на основному наборі;
- виконання еталона на основному наборі (або збережений результат);
- різниця на основному наборі (`compare.compare`, без урахування порядку);
- різниця з урахуванням порядку;
- дерево запиту студента й еталона (`compose.parse_query`), набір конструкцій;
- вердикт по кожному прихованому набору (`_matches_on_dataset`, як зараз: EXCEPT ALL
  у базі, інакше Python);
- стани таблиць для режиму зміни даних (`run_sequence`, як зараз).

### 5.3. Семантика критеріїв

| id | Пройдено, якщо | Пояснення при провалі |
|---|---|---|
| `execution` | запит виконався без помилки | текст помилки |
| `columns` | кількість стовпців збігається | «очікується N, отримано M» |
| `column_names` | назви стовпців збігаються без урахування регістру, попарно за позицією | які не збіглися |
| `complete` | `diff.missing` порожній | до 3 відсутніх рядків |
| `precise` | `diff.extra` порожній | до 3 зайвих рядків |
| `order` | послідовність рядків збігається з еталоном | «рядки правильні, порядок інший» або «спершу виправте набір рядків» |
| `reads_data` | `compose.reads_data(student_node)` | «запит не звертається до таблиць» |
| `state` | усі таблиці збігаються з еталонним станом | перелік таблиць, що відрізняються, до 3 рядків на таблицю |
| `dataset:k` | збіг на k-му прихованому наборі | `targets` набору або «не збіглося на контрольних даних» |
| `require:KW` | конструкція є в дереві або в тексті без літералів | «не використано KW» |
| `forbid:KW` | конструкції немає | «використано заборонене KW» |

Залежності:

- `execution` не пройдено: усі інші критерії не пройдено з поясненням «запит не виконався».
- `columns` не пройдено: `column_names`, `complete`, `precise`, `order`, усі `dataset:k`
  не пройдено з поясненням «кількість стовпців не збігається». Приховані набори при цьому
  не запускаються (та сама схема, та сама помилка).
- `complete` або `precise` не пройдено: `order` не пройдено з поясненням «спершу виправте набір рядків».
  Приховані набори запускаються (на інших даних результат теоретично може збігтися).
- Еталон не виконався: усі критерії, крім `execution`, не пройдено з поясненням
  «еталонний запит не виконується, повідомте викладача»; у `feedback.message` те саме.
- Обрізаний результат (понад 1000 рядків) на базі з EXCEPT ALL: `complete` і `precise`
  обчислюються з симетричної різниці в базі (обидва пройдено, якщо різниця порожня, обидва
  не пройдено інакше), `order` не пройдено з поясненням «результат завеликий для перевірки порядку».
  На базах без EXCEPT ALL `complete`, `precise`, `order` не пройдено з поясненням «результат завеликий».
- Бюджет прихованих наборів 45 с: набори, що не встигли, не пройдено з поясненням
  «перевірку не встигли виконати».
- Кілька інструкцій або інструкція зміни даних замість SELECT: `execution` не пройдено
  з поясненням форми запиту, без виконання.

### 5.4. Результат

```python
@dataclass
class CriteriaResult:
    items: list[dict]        # {"id", "name", "passed", "detail"}
    passed_count: int
    total: int
    threshold: int
    passed: bool             # passed_count >= threshold
```

`grading.service.grade()` зберігає сигнатуру `grade(task, student_query, run, run_sequence=None) -> GradeResult`.
`GradingTask` отримує поле `criteria: dict`. `GradeResult.feedback`:

```json
{
  "mode": "result | execution",
  "criteria": [{"id": "...", "name": "...", "passed": true, "detail": ""}],
  "checks": "той самий список, що criteria (сумісність)",
  "passed_count": 6, "total": 7, "threshold": 6,
  "message": "Зараховано: 6 із 7  |  Не зараховано: 4 із 7, потрібно 6",
  "hints": [], "missing_rows": [], "extra_rows": [],
  "failed_datasets": [], "keywords_missing": [], "forbidden_used": [],
  "result_match": true
}
```

Підказки формуються з пояснень критеріїв, що не пройдені. `result_match` = `complete` і
`precise` пройдені (або `state` для зміни даних).

Із `service.py` зникають ваги, Жаккар, `PARTIAL_RESULT_CAP`, `HIDDEN_FAILURE_RATIO`,
`NOT_PASSED_CAP`. `compare.py`, `normalize.py`, `compose.py`, `mutants.py`, `runner.py`
лишаються, `runner.build_task` передає `criteria`.

## 6. API

- `LessonExerciseSerializer`, `AssignmentSerializer` (викладацькі та create-серіалізатори):
  поле `criteria` з валідацією з розділу 4.1. Для студентів поле `criteria` не віддається
  (воно не розкриває розв'язок, але й не потрібне), натомість read-only
  `criteria_summary`: `{"criteria": [{"id", "name"}], "threshold": N}` з `describe()`.
  Для викладача віддаються обидва.
- `GET /api/grading/criteria/`: каталог загальних критеріїв
  `[{"id", "name", "description", "kinds": ["select", "dml", "nosql"]}]`
  для форми. Доступ: автентифіковані користувачі.
- `submissions/views.py`: передає `criteria` у `build_task`. Перед збереженням
  `submission.result` рядки приводяться до JSON-сумісних типів: Decimal у число
  (int, якщо ціле, інакше float), date/datetime/time у ISO-рядок, bytes у hex,
  інше через `str`. Це виправляє підтверджену помилку HTTP 500 на NUMERIC і датах.
- `courses/views.py: validate_exercises` без змін.

## 8. Фронт

### 8.1. Типи та API

- `ExerciseCriteria {enabled: string[]; threshold: number}`,
  `CriteriaSummary {criteria: {id: string; name: string}[]; threshold: number}`,
  `CriterionInfo {id, name, description, kinds}`.
- `SubmissionFeedback`: `criteria`, `passed_count`, `total`, `threshold`.
- `api/grading.ts: getCriteriaCatalog()`, хук `useCriteriaCatalog()`.
- `LessonExercise`, `Assignment`: `criteria?`, `criteria_summary?`.
- `lib/schemas.ts`: `criteria: z.object({enabled: z.array(z.string()), threshold: z.number().int().min(0)})`
  з замовчуванням; `order_matters` лишається в схемі, не показується.

### 8.2. Форма викладача (`LessonFormPage`, вправа)

Блок «Критерії оцінювання»:

- галочки загальних критеріїв з каталогу, відфільтровані за типом бази курсу і видом еталона
  (вид визначається на клієнті за першим словом еталона: INSERT/UPDATE/DELETE/CREATE дає `dml`,
  інакше `select`; сервер валідує остаточно);
- `execution` показаний увімкненим і неактивним;
- `order` показаний з приміткою «еталон має містити ORDER BY»;
- нижче похідні рядки без галочок: «Контрольний набір №k: назва», «Використано KW»,
  «Не використано KW» з підписом «керується списком наборів / ключових слів»;
- поле «Достатньо N з M»: M = увімкнені загальні + похідні, рахується на клієнті;
  за замовчуванням N = M; при зміні M значення N підрізається до M.
- Галочка «Порядок рядків важливий» видаляється.

Нова вправа отримує `criteria` за замовчуванням, розраховане на клієнті тим самим правилом,
що й на сервері (усі застосовні, крім `column_names`). Для старої вправи з порожнім `criteria`
форма показує те саме замовчування і зберігає його явно.

### 8.3. Студент (`LessonPage`, `AssignmentPage`)

- До здачі, у картці завдання: «Критерії: M, достатньо N» і список назв.
- Після здачі: заголовок «Пройдено 6 із 7» зеленим або «Пройдено 4 із 7, потрібно 6» червоним,
  далі кожен критерій рядком ✓/✗ з назвою і поясненням, далі підказки як зараз, бал.
- Історія спроб показує «k із M» поряд із балом.

Нові рядки локалізації в `lessons.json` (uk, en). Назви критеріїв приходять із сервера.

## 9. Тести

Бекенд (`--settings=config.settings_test`, SQLite):

- `grading/test_criteria.py`: кожен критерій окремо на `sqlite_runner`; залежності
  (помилка виконання, невідповідність стовпців, рядки перед порядком); еталон не виконується;

- `sandbox/test_grading_engines.py`: оновити очікування балів, додати на PostgreSQL кейс
  зі стовпцем NUMERIC і DATE через повний шлях відповіді (`SANDBOX_INTEGRATION=1`).

Фронт: `npm run build` без помилок, ручна перевірка в браузері: форма викладача зберігає
критерії й поріг, студент бачить список і результат «k із M», старий урок без налаштувань
працює як раніше.

## 11. Поза межами

Ваги критеріїв, обов'язкові («критичні») критерії, ручне коригування бала викладачем,
перерахунок старих відповідей, перегляд критеріїв у звіті викладача. Усе це можна додати
поверх реєстру пізніше.
